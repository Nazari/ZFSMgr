## ZFSMgr 2.0.0rc1 — the graphical interface, in Java (release candidate)

The first version with a graphical interface again. **It is a release candidate**: the
command line client (`zfsmgr-cli`) and its daemon (`zfsmgr-agent`) are as solid as in 1.4;
the interface is new and may have bugs. The CLI is still the reference: whatever the
interface does, it does by running `zfsmgr-cli` lines.

Asset: `zfsmgr-2.0.0rc1.zip` (+ `.sha256`): CLI, daemon **and the interface**, one installer
per system inside. There is no CLI-only package any more.

**Update every machine**: after installing the new client, run `install-daemon -a`.

### The interface: one Java program for every system

`zfsmgr-gui` is a Java 21+ program (Swing with FlatLaf): the same `.jar` on Linux, macOS,
Windows and —for the first time— FreeBSD. It needs **Java 21 or later** (for instance
[Temurin 21](https://adoptium.net); on FreeBSD the `openjdk21` port). The installers put it
in place even without Java, and `zfsmgr-gui --check` says whether it finds one.

- Linux and FreeBSD: `zfsmgr-gui`, and an entry in the desktop's menu.
- macOS: `/Applications/ZFSMgr.app` (a small bundle that starts the `.jar`) and `zfsmgr-gui`.
  The Qt bundle of 1.x is replaced; `zfsmgr-cli` is now installed standalone.
- Windows: a Start menu shortcut and `zfsmgr-gui.cmd`. The Qt Setup of 1.x, if present, is
  uninstalled first.

Its pages: **Status** (machines, pools, copies and what needs attention), **Copies** (each
copy between machines, with copy now, pause, change and stop, and a wizard for a new one),
**Machines** (machine → pool → dataset, with snapshots, files and, in advanced mode,
properties, management, sending and organizing), **Jobs** (running and finished), and
**Administration** in advanced mode (connections, the programs on each machine, which daemon
reaches which by itself, the security keys that open ZFSMgr, and the language).

### New since 1.4.3

- **One configuration for the whole network** (optional): `zfsmgr-cli network seed` on one
  computer makes its configuration the network's, kept by every daemon; `network join` on
  the others. Every computer then sees the same machines, and a change made on one reaches
  the rest. The secrets travel encrypted with the network's data key, which no daemon has,
  and the document is signed with it. Without seeding, each computer keeps its own
  configuration, as before. A machine is called by its name everywhere: there is no «local»
  any more in a network.
- **Security keys**: a FIDO2 key (any brand with `hmac-secret`) can open ZFSMgr instead of
  typing the master password (`master-key add`). The secrets are now under a random data
  key wrapped by the master password and by each key.
- **One session per machine**: ZFSMgr warns when it is open on another computer, and that
  other session can be asked to close.
- **A computer without ZFS** is a client of the others: no local connection is forced on it.
- `probe`: whether a connection works and what is on the other side, as fixed codes.
- `peers --check`: whether each daemon reaches the others by itself.
- Confirmations say what is lost, and what cannot be undone asks for the name typed.

### Fixes

- The CLI never spends a smart card's PIN tries on the sudo password (macOS with a PIV card
  paired to the account).
- `--serve` no longer lost every command's output on Windows without administrator rights.
- The Windows daemon install fails, instead of reporting success, when the agent does not
  start (an antivirus taking it, for instance).
- macOS: the agent keeps its stable signature, and with it the «Full Disk Access» granted.
- A levelling schedule whose destination is the same machine works when the daemon was
  given its credentials under another name.
