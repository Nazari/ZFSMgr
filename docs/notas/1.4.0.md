## ZFSMgr 1.4.0 — command line

Still the command line client (`zfsmgr-cli`) and its daemon (`zfsmgr-agent`) only.

Asset: `zfsmgr-cli-1.4.0.zip` (+ `.sha256`), one installer per system inside.

**Update every machine**: after installing the new client, run `install-daemon -a`. Pulling
needs the new daemon on both ends, and the reinstall is what creates each machine's pull
certificate.

### New: schedules that PULL

Until now the source of a schedule pushed its snapshots to one target. Now the TARGET can pull
them: the backup machine starts the copy itself, one source can have several copies, and each
copy keeps its own retention.

```
# on the backup machine, on an empty dataset:
schedule --daily 30 --origin zfsm://server/tank/data
```

- The origin must have its own schedule. The copy brings its whole tree, dataset by dataset,
  keeps 30 dailies while the origin keeps its own number, and new datasets arrive with
  `canmount=noauto`, so they never mount by themselves on the backup.
- The stream travels on the connection the backup opens: it needs no open port, and the
  origin does not need to know its address.
- The origin holds each copy's base (`zfs hold zfsmgr-pull:…`), so a copy that is switched
  off for longer than the origin's retention catches up by itself. On the origin,
  `schedule --pullers` lists who pulls copies, and `schedule --release-puller <tag>`
  releases a copy that is gone.
- When the schedule is written, the CLI checks what the first pass would only find out: the
  backup's daemon reaches the origin's with its own credentials, both daemons are up to date,
  the origin is scheduled and not already pushing there, there is no cycle, and the space
  (a warning).
- `schedule status` says «pulled ok»; `schedules` has an ORIGIN column.

### New: a pull credential

`peers --push --role pull --on zfsm://backup` hands the backup machine only a PULL credential
for each other machine. With it, a daemon answers only what pulling needs —look at the
snapshots, send them, hold its own base— and refuses everything else: no destroy, no
rollback, no set, no jobs. A backup machine that is broken into cannot erase what it backs up.
Without `--role`, `peers --push` hands over the full credentials as before, which is what a
schedule that pushes needs.

### Fixed

- **The scheduler no longer prunes or renames a snapshot another machine holds as its base.**
- **The battery** took JSON from output mixed with warnings, and used a global `sync`.
